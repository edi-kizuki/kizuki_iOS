# Independent review: architecture concept v1

Scope: `docs/concept/2026-10-25-architecture-concept-v1.md` (cited as `C:line`) checked against the interview (`I:line`), Notion extracts (`NT:line` = `docs/context/2026-10-25-notion-technical-extracts.md`, `NS:line` = `docs/context/2026-10-24-notion-source-extracts.md`), research (`RBE:line`, `RIOS:line`), Figma walkthrough (`FIG:line`), playbook (`PB:line`) and the repo. Reviewer did not write the concept and did not see its reasoning.

Severity: **blocker** = must be fixed before build tickets are cut (violates a locked decision, leaks private data, breaks the core loop, or touches production). **major** = will cause rework, a security gap or a review rejection if left. **minor** = clarity, consistency, small correctness.

## Verdict

v1 is buildable after fixes. It complies with every locked decision I checked (D1–D39 and the agent defaults). It contains everything playbook §5 asks for: problem, users, design, flows, data model, v0 vs later, risks, open decisions, slices, five diagram specs and a screen list with no look. Repo facts are mostly accurate: supabase-swift `exact: 2.55.4`, one migration with 10 pgTAP tests, handle 3–24, the `config.toml` flags, CI jobs, the `AppConfiguration` rules, 21 `@Test` + 2 UI tests, `UITestBackend` in `KizukiApp.swift` and the global `.preferredColorScheme(.dark)` all match. The exceptions are C-22 and C-34.

There are no blockers. The weak spots are the paths a happy-path design skips:
- concurrent and late request transitions;
- the push pipeline's trust boundary;
- how a live backend exists for S03–S08 and for staging;
- a privacy model contradicted by its own match reasons.

Scope is the main delivery risk. It should be cut in v2, not just flagged.

## Top 5 must-fix

1. **C-13:** decide the live-backend path for the critical path (resolve 005 as a wave-0 gate, or define what proves S03–S08 end to end in CI). Today the first live slice is blocked.
2. **C-01:** reconcile match reasons with the privacy model (city, availability, work mode) before reason codes are frozen in wave 0.
3. **C-04, C-05, C-06:** make `respond_request` lock rows, re-validate on accept, handle deleted counterparts, and define the reopen of a closed pair conversation.
4. **C-02, C-10 (with C-03):** lock `send-push` to the webhook, make device tokens single-owner and cleared on sign-out, and make webhook setup environment-safe.
5. **C-15, C-14 (with C-16):** add a hard v0 production guard and ref-pinned staging scripts that cover seeding, auth config, functions and secrets.

Next after these: C-18 / C-19 (cut scope and thin S01) and C-12 (zero-taste band rule so S06 shows a feed).
